01 Context

왜 이 프로젝트가 중요했는가

클럽미니쉬는 미니쉬 치과의 기존 고객(초대인)이 지인을 초대하고, 초대받은 지인(피초대인)이 상담 예약부터 리워드 수령, 그 혜택으로 이어지는 재예약까지 하나의 앱에서 끝낼 수 있는 멤버십 기반 헬스테크 서비스이다.

MVP1 비즈니스 목표

초대인과 피초대인 모두가 끊김 없이 예약을 완료할 수 있는 흐름 구축
초대인은 포인트 혜택 사용 시, 피초대인은 초대장 수령 후 상담 신청 시
예약 흐름의 원활함이 서비스 전체 전환의 핵심 전제 조건이었다.

MVP1 단계에서 가장 큰 과제는 초대 → 상담 신청 → 예약 확정 → 방문 확인 → 리워드 지급으로 이어지는 전체 흐름이,
사용자 관점에서는 하나의 경험처럼 느껴지지 않는다는 점이었다.
링크를 클릭한 피초대인이 "지금 내가 예약을 한 건지, 신청만 한 건지, 다음에 뭘 해야 하는지"를 명확히 이해하지 못한 채 이탈하는 패턴이 반복됐다.
초대인은 지인이 어디까지 진행했는지 확인할 방법이 없었고,
CS는 신청 접수부터 예약 확정까지 모든 단계를 수동으로 처리해야 했다.

02 Research

무엇을 조사했고, 무엇을 발견했는가

조사 방법 규모 인터뷰 방식 목적
피초대 사용자 인터뷰4명대면예약 플로우 이탈 원인 및 상태 인지 문제 파악
초대인 (기존 고객) 인터뷰2명대면초대 후 진행 상황 불투명 문제 파악
CS / 운영 담당자 인터뷰2명대면운영 병목 구조 및 수동 처리 포인트 파악
기존 플로우 / 정책 문서 분석——서비스 전체 구조 및 예약 정책 이해
예약 신청 시나리오 점검——AS-IS 플로우의 구조적 마찰 지점 도출
상태값 / 리워드 정책 매핑——운영 상태값과 사용자 언어 간 괴리 분석
교차 검증(Triangulation) — 표본(n=8) 한계를 인지해, 인터뷰 8건 × 4주치 CS 티켓 로그 × 예약 정책 문서 11종을 3축으로 교차 비교해 인사이트를 도출했다. * n=8은 정성 인사이트 도출을 목적으로 한 의도된 규모이며, 정량 일반화를 목적으로 하지 않는다.
01
4/8명사용자는 혜택보다 "지금 내가 뭘 해야 하는지"를 먼저 알고 싶어 한다. 초대 메시지를 받았을 때 첫 질문은 "예약이 된 건가, 신청만 하는 건가?"였다.
[관찰 메모] 사용자가 첫 화면 진입 직후 "이게 끝인가요?"라는 표정을 보임 — 라이브 UT, 30대 직장인

교차 검증 — CS 티켓 동일 패턴 확인 / 정책 문서 '신청 ≠ 예약' 표기 누락

02
3/8명신뢰 형성 전 개인정보 입력 요구가 이탈 위험을 높인다. 이름·번호·메모·병원 선택이 초반에 몰리면 사용자는 부담을 느낀다.
"이름이랑 번호까지는 그렇다 쳐도, 병원까지 바로 골라야 하니까… 그냥 나가게 되더라고요." — 피초대인, 30대 직장인

교차 검증 — 인터뷰 3/8명 동일 패턴 / 플로우 문서 초반 입력 필드 5개 확인

03
3/8명발행·전송·신청·확정·완료 같은 상태값이 사용자 언어가 아니다. "나는 지금 어디 있는지" 이해하기 어렵다는 피드백이 반복됐다.
"제가 보낸 초대가 '발행됨'이라고 나오는데, 상대방이 받은 건지 신청한 건지 전혀 모르겠어요." — 초대인, 36세 직장인

교차 검증 — CS 티켓 "상태 확인" 문의 반복 / 정책 문서 내부 용어와 화면 표기 불일치

04
2/4명초대인은 피초대인의 진행 상황을 알 수 없다. 초대를 보낸 후 결과를 확인할 방법이 없어 리워드 기준도 불명확하게 느껴졌다.
"초대장을 보내고 나서 상대방이 예약했는지 아닌지를 제가 알 수가 없어요." — 초대인, 30대 직장인

교차 검증 — 초대인 2/2명 동일 언급 / 앱 화면 상태 표시 없음 확인

05
2/2명운영 측면에서 수동 확인 포인트가 5개로, CS 개입이 잦다. 운영 마찰이 결국 사용자의 느린 확정 경험으로 돌아왔다.
"신청이 들어오면 저희가 일일이 확인하고 연락해야 해서, 하루에도 몇 번씩 같은 작업을 반복해요." — CS 매니저

교차 검증 — CS 매니저 2/2명 동일 언급 / 운영 프로세스 문서 확인

05-1 문제 1 정의 · 예약 흐름이 너무 복잡했다

10단계에 달하는 예약 흐름,
사용자는 중간에 멈췄다

초대 링크를 클릭한 피초대인이 상담 신청을 완료하기까지 총 10단계를 거쳐야 했다. 별도 인증 화면의 마찰, 지점·날짜·시간·상담분야가 각각 독립된 화면으로 분리된 구조가 이탈의 주요 원인이었다.

05-2 문제 1 해결안 · 인지 단계를 재정의했다

기능을 줄인 게 아니라 인지 단계를 재정의했다

10단계를 6단계로 줄인 것의 본질은 화면 수 감소가 아니다. 사용자가 경험하는 "결정 포인트"를 재정의하고, 그 사이를 하나의 흐름으로 연결한 것이다.

05-3 문제 2 정의 · 예약 완료 이후가 블랙박스였다

"지점에서 전화드려요" 이후
사용자는 아무것도 몰랐다

예약 흐름의 복잡함은 피초대인만의 문제가 아니었다. 신청이 완료된 이후에도, 초대인은 상대의 진행 상황을 알 수 없었고 CS는 모든 확인을 수동으로 처리해야 했다. 세 역할 모두에게 '지금 어디까지 됐는지'가 보이지 않는 구조였다.

05-4 문제 2 해결안 · 예약 상태를 앱에서 실시간으로 보여준다

예약 완료 후에도
사용자는 다음을 알 수 있다

기존에는 "지점에서 전화드려요" 이후 앱에서 예약 상태를 확인할 방법이 없었다. 예약신청 → 전화상담 → 예약완료로 이어지는 3단계 상태를 앱에서 실시간으로 표시해, CS가 처리할 때마다 사용자가 즉시 현재 위치를 파악할 수 있도록 개선했다.

Decision Log — 왜 이렇게 설계했는가
1

예약 진행 상태 실시간 표시 — 초대인·피초대인 모두 예약 신청 이후 상태를 알 수 없어 CS 문의가 반복됐다. 3단계 스텝 바로 현재 위치를 즉시 파악하게 하고, 대기 시간을 명시해 불필요한 확인 문의를 차단했다.

“초대장을 보내고 나서 상대방이 예약했는지 아닌지를 제가 알 수가 없어요.” — 초대인, 30대 직장인
2

CS 운영 확인 포인트 5→3 재구성 — 수동 확인 포인트를 줄여 CS 개입 없이도 사용자가 상태를 파악할 수 있는 구조로 전환했다. CS 담당자 인터뷰에서 "신청 직후 재문의 전화"가 반복 업무의 핵심이라는 점을 확인하고 설계에 반영했다.

AS-IS
예약 신청 완료
"지점에서 전화드려요" — 언제 오는지, 얼마나 기다려야 하는지 알 수 없었다. 사용자는 전화가 올 때까지 막연히 기다려야 했다.
TO-BE 01 — 신청 직후
예약신청 → 전화상담 → 예약완료
신청 완료 즉시 3단계 스텝 바로 현재 위치를 표시한다. "1~2시간 안에 지점에서 전화드려요. 평일 18시 이후 신청은 다음 영업일 오전에 연락드립니다." 안내로 대기 시간을 명시한다.
TO-BE 02 — 예약 확정 후
CS 처리 완료 → 예약 확정
CS가 확정 처리하면 스텝 바 전체가 완료로 업데이트된다. 예약 일시·지점·담당자 정보를 즉시 확인할 수 있다.

"1~2시간 안에 지점에서 전화드려요.
평일 18시 이후 신청은 다음 영업일 오전에 연락드립니다."

② 전화상담 상태 레이블: 상담 진행 중

"지점에서 일정을 조율하고 있어요.
곧 확정 안내를 드릴게요."

'처리 중'이 아닌 구체적 주체(지점)를 명시해 사용자 불안 감소. 다음 액션(확정 안내)도 예고.
③ 예약완료 상태 레이블: 예약 확정

"예약이 확정됐어요.
방문 전날 알림을 드릴게요."

운영 마찰 감소
웹 플로우 배포 이후, CS 매니저로부터 "신청 직후 재문의 전화가 눈에 띄게 줄었다"는 구두 피드백을 받았다. 기존에는 "제가 예약이 된 건가요?"류의 확인 문의가 신청 건마다 반복됐는데, 완료 화면에 3단계 스텝 안내를 추가한 이후 해당 패턴이 감소했다.
CS 업무의 75%를 차지하던 예약 확인 영역을, 운영 확인 포인트 5→3 재구조화로 직접 줄였다. 내부 운영 로그 기준, 표본 4주 / 정성 관찰
📋
입력 데이터 품질 개선
고객 정보 입력 단계를 인증 화면 제거 이후로 재배치한 결과, CS팀에서 "추가 확인 전화를 해야 할 만큼 정보가 부정확한 케이스가 줄었다"는 반응이 있었다. 사용자가 흐름을 이해한 상태에서 입력하게 되면서 입력 완성도가 높아진 것으로 판단된다. 배포 이후 예약 완료까지의 평균 소요 시간이 단축되었고, 완료율도 개선되는 추세를 보였다.

07 Reflection

이 프로젝트에서 얻은 것

배운 것
단계를 줄였더니 전환이 늘어난 게 아니라,
사용자가 자신이 어디 있는지 알게 됐을 때 전환이 늘었다.
  • 화면의 단순화만으로는 예약 전환이 개선되지 않는다. 실제 전환의 핵심은 사용자가 현재 상태를 이해하고 다음 행동을 확신하게 만드는 구조 설계였다.
  • 단계 수를 줄이는 것보다 각 단계의 역할을 명확히 하는 것이 더 중요했다. "기능 삭제"보다 "인지 단계 재정의"가 핵심이었다.
  • 혜택은 진입 동기, 예약은 그 동기를 즉시 행동으로 잇는 트리거다. 둘을 같은 흐름 위에 두었을 때 전환은 설계된다.
