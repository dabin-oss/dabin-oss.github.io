02 Design System

일관된 경험을 만드는
기반 작업

0→1 프로젝트이기 때문에 시각 언어를 처음부터 정의해야 했습니다. 컬러·타이포·간격 시스템을 먼저 확정하고, 이를 기반으로 재사용 가능한 컴포넌트를 구축해 모든 화면 설계에 적용했습니다.

01
Grayscale 10단계
배경·카드·텍스트를 위한 10단계 그레이스케일 팔레트. 화면 간 일관된 계층 구조를 유지하기 위해 각 역할별로 값을 고정했습니다.
02
4px 스페이싱 시스템
모든 여백과 간격을 4px 단위로 통일. 개발자가 Figma Dev Mode에서 수치를 직관적으로 읽을 수 있도록 설계했습니다.
03
한/영 타이포그래피
한국어(Pretendard)와 영어(Roboto)를 각각 지정하고 6단계 타입 스케일을 정의. 멀티 언어 서비스 특성을 반영했습니다.

04 Remote Collaboration

원격의 제약을
구조로 극복했습니다

해외 지사 개발팀과 물리적으로 떨어진 환경에서 협업했습니다. 실시간 구두 소통이 제한된 만큼, 디자인 의도를 오해 없이 전달하는 것이 핵심 과제였습니다.

방식
시각화
텍스트 대신 플로우 다이어그램으로 전달
말로 설명하기 어려운 인터랙션과 상태 변화는 플로우 다이어그램과 화면 어노테이션으로 시각화했습니다. '상태값이 unknown일 때 어떻게 노출할까?' 같은 엣지 케이스는 Figma 안에 상태 화면과 조건을 함께 구조화해 전달해, "이렇게 해주세요"가 아니라 "이 화면에서 이 상황일 때 이렇게 보여야 합니다"를 그림으로 만들었습니다.
방식
구조화
QA 피드백을 맥락과 함께 구조화
모든 피드백과 QA 이슈는 다우오피스로 주고받았습니다. 해외 지사 개발팀과는 영어로, 국내 PM과는 한국어로 맥락을 구분해 전달했고, 단순 수정 요청 나열 대신 어떤 화면의 어떤 상태에서 발생하는 문제인지를 함께 명시해 재질문이 발생하지 않도록 했습니다.
방식
설득력
근거 있는 디자인 결정으로 신뢰 구축
원격 환경에서는 "왜 이렇게 설계했는가"를 문서로 남겨야 했습니다. 예를 들어 인증 단계 제거 결정 시, 유저 인터뷰 인용 3건과 보안 리스크 한 줄을 함께 첨부해 근거를 전달했고, 이 과정이 개발팀과의 신뢰 관계를 만들었습니다.
05 Launch & After

출시 그리고 그 이후

iOS / Android · Web(피초대인) 출시 후 첫 주 실사용 피드백을 직접 수집하고 대응했습니다. 런칭이 끝이 아니라 개선 사이클의 시작이었습니다.

사용자 멘탈 모델 변화 CS 매니저 구두 피드백 기준 정성 관찰(GA 미비)
예약 완료 화면에 3단계 스텝 안내를 추가한 이후, "제가 예약이 된 건가요?" 류의 반복 확인 문의가 눈에 띄게 줄었습니다. 상태 표시가 사용자의 불안을 없애고, 다음에 해야 할 것을 알게 만드는 설계 효과를 실운영에서 확인한 사례입니다.
사용자 학습 상태 인지 개선
운영 사이드 임팩트
CS 운영 확인 포인트를 5단계 → 3단계로 재구조화한 결과, CS 매니저의 1건당 처리 시간이 줄었습니다. 사용자 플로우를 바꾼 결정이 운영팀의 업무 구조에도 직접 영향을 준 사이드 임팩트였습니다.
